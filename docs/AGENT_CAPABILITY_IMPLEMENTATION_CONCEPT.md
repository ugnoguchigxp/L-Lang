# S-LANG：エージェントが能力を製造・検証・配備する実装コンセプト

2026-09-15。ユーザーとの責務分担の合意を基にした今後の設計方針。以下の新機能は未実装であり、実装済み仕様とは区別する。

会話ではS-LANG、既存リポジトリではL-Langという名称を使っている。本書は同じプロジェクトの将来方針を扱い、パッケージやCLIの一括改名は行わない。

## 1. 目標と設計の中心

SAAAのような対話エージェントが、ユーザーの目的から不足する能力を見つけ、Coding Agentへ製造を依頼する。Coding Agentは自然言語の仕様から実装とテストを製造し、Wasmを実行して検証する。SAAAは提出物が自分のスキルとして目的を達成できるかを検証し、合格した版を配備する。不合格なら再現情報とともに修正を依頼する。利用中の結果も次の改善へ戻す。

S-LANGは、この循環を支える自然言語の仕様、検証可能な実行表現、Wasm、検証記録の基盤になる。自然言語を任意の動作へ無条件に変換する保証ではなく、対応する実行範囲と確認できた条件を明示した能力を製造する。

通常の能力呼び出しにはLLMを必要としない。目的の整理、製造、修正、SAAAの判断にはLLMを利用し得る。SAAA自身やCoding Agent全体をWasmへ変換する構想ではない。

## 2. 責務と変更権限

| 担当 | 責務 | 判定・変更の境界 |
| --- | --- | --- |
| SAAA | 会話から目的・受け入れ条件を整理し、能力の発見・呼び出し・組み合わせを試す | 受け入れ条件、利用権限、配備方針を管理し、配備可否を決める |
| Coding Agent | 仕様から実装コードとテスト検証コードを製造し、コンパイルしたWasmを実行検証する | 候補を提出できる。SAAAの受け入れ結果や配備状態を自分で合格に書き換えない |
| S-LANGのツール群 | schema・型・IR・成果物対応・実行制約を検査し、テストを実行して記録する | モデルの「成功した」という文章を実行証拠として扱わない |
| ホスト・能力レジストリ | 隔離実行、権限制御、対象版の選択、配備・無効化・復旧を実施する | SAAAの判定と運用方針に従って状態を変更する |
| 人間 | 目的を伝え、エージェントが解消できない意図や権限の選択を必要に応じて回答する | 毎回のコードレビューやテスト承認を必須にしない |

SAAAとCoding Agentの分離は、特定のモデル製品への依存ではなく、入力、成果物、変更権限の分離として実装する。同じファイルを自由に編集できるだけの構成では承認境界にならないため、配備API側で検査する。

## 3. 能力として提出する単位

既存のPrompt Source、Resolution Lock、Build Manifest、Wasmを再利用し、その外側に能力パッケージを追加する。以下は論理構成であり、ファイル名やschemaの確定は実装計画で行う。

| 構成物 | 含める情報 |
| --- | --- |
| 能力仕様 | 能力ID、版、目的、利用する状況、利用しない状況、要求ID、入力・出力、失敗の扱い |
| 実装 | Prompt Source、解決済みIR、Lock、Wasm、コンパイラとABIの版 |
| 部品テスト | 要求IDに対応するケース、期待値、性質、境界条件、テスト検証コードと実行方法 |
| 利用契約 | 必要なホスト機能、依存する能力と版、資源上限、状態・副作用の有無 |
| 提出記録 | 各構成物のhash、検証器の版、実行結果、失敗・未実行項目 |
| SAAA受け入れ記録 | シナリオと判定基準の版、対象成果物hash、観測結果、合否・理由 |

テスト検証コードは初期段階ではホスト側で動かしてよい。テストまでWasm化することを前提にしない。S-LANGの実装の正本は自然言語SourceとIRであり、任意のTSコードを実行本体にする経路へ戻さない。

hashは整合性確認であり、提出者の真正性の保証ではない。外部配布へ拡張する際は、認証・署名・信頼する発行元の管理を別途設計する。

## 4. 二段階の検証

### Coding Agent：部品として要求どおりに動くか

実装とテストをそれぞれ製造できるようにする。テストは実装の出力を正解としてコピーせず、要求と入力契約を基に作る。対応する有限領域では全列挙、それ以外では境界値・性質・反例探索を組み合わせる。

- 正常系、拒否すべき入力、欠損・null等の境界を、実際のWasmを通して実行する。
- 参照IRの実行結果との比較でコンパイル時の意味の変化を検出する。ただし、両者が共有する要求の誤解は検出できない。
- 条件を一つ外す、否定を反転する等の意図的な誤実装をテストが検出できるか確認する。生き残った変更には理由を記録する。
- 通常buildのモデル呼び出し不要、成果物の対応、不正入力拒否、対応外操作の拒否を維持する。

生成テスト自体も誤る可能性がある。要求ごとの検証対応と未検証箇所を提出し、テスト件数やカバレッジだけで要求充足を宣言しない。生成したテストコードも隔離し、ネットワーク・ファイル・実行時間を制限する。

### SAAA：自分の能力として使えるか

受け入れシナリオと判定条件を、候補の結果を見る前に保存する。Coding Agentのテストを再実行するだけでなく、通常の能力検索・呼び出し経路を使い、目的に沿う結果へ到達できるか確認する。

- 能力の説明から適切に選択でき、入力を組み立て、出力やエラーを解釈できるか。
- 実際のタスクを模した入力と既存スキルの組み合わせで、期待する結果になるか。
- 適用範囲外では、誤って成功として扱わず、失敗や未対応を上位へ返せるか。
- 定めた権限、時間、容量の範囲で利用できるか。

可能な判定は機械実行する。自由文の有用性などモデル判定が必要な場合は、その基準と不確実性を記録する。初期の自動配備は機械判定できる条件判定能力に絞り、曖昧なモデル評価だけで配備しない。

SAAA用の非公開ケースは候補へ渡さない。ただし失敗を修正依頼として開示したケースは、以降は既知の回帰テストとして扱い、未知ケースへの成功の証拠とは区別する。

## 5. 配備と修正の循環

候補作成 → 部品検証合格 → SAAA受け入れ合格 → 配備済み、の順に状態を進める。失敗時は候補を修正へ戻す。検証エラーや実行不能は合格にしない。仕様不足は追加質問、表現不能は未対応として区別する。

受け入れ結果はSource・Wasm・テスト・利用契約・受け入れ条件の版に結び付ける。変更された候補へ古い合格結果を流用しない。配備操作直前にも対象の一致を確認し、登録先を原子的に切り替える。配備先はまずローカルの能力レジストリとし、クラウド環境への公開は別段階とする。

修正依頼には、要求ID、対象版、再現入力、期待結果、実際の結果、失敗段階、ログを含める。Coding Agentは再現テストを追加して修正し、新しい候補として提出する。受け入れ条件の変更が必要ならSAAAへ仕様変更を提案し、合格のために勝手に緩めない。

最大修正回数、モデル利用予算、実行時間を実行開始時に固定し、上限で停止・保留する。改善がない反復も記録する。自律的に改善することと、無制限に再試行することを分ける。

配備後は利用成否、エラー、所要時間を観測し、問題のある版を無効化または旧版へ切り戻す。旧版へ切り戻しても、既に行った外部操作が取り消されるわけではない。副作用のある能力には後述の別設計が必要になる。

## 6. 機能拡張の順序

| 段階 | 追加する機能 | 完了を判断する実行証拠 |
| --- | --- | --- |
| F1 能力の提出契約 | 能力パッケージschema、機械可読の検証結果、CLI/API、要求とテストの対応 | 既存Predicateを候補として提出でき、不足物・hash不一致を拒否できる |
| F2 部品テストの製造 | Coding Agent用の実装・テスト製造プロトコル、Wasmテストrunner、反例と修正依頼形式 | 意図的な誤実装を検出し、修正版を同じ条件で再検証できる |
| F3 SAAA受け入れと配備 | ホストadapter、シナリオrunner、二段階判定、ローカルレジストリ、切り戻し | 部品テスト合格でも受け入れ失敗なら配備されず、修正後に登録・通常呼び出しできる |
| F4 利用を通じた改善 | 版ごとの観測、回帰テスト化、停止条件、依存版固定 | 利用失敗から修正依頼と再配備へ進み、反復上限や依存変更で正しく停止する |
| F5 純粋処理の表現拡張 | 数値比較・計算、構造化出力、文字列、配列・record変換を必要な順に追加 | 既存profileでは表せない具体的タスクを、新しいprofileの意味・ABI・資源制約とともに検証できる |
| F6 外部機能と連携 | 明示的なhost capability、外部API、状態、複数能力の連携 | 権限外操作の拒否、timeout、重複操作防止、失敗時の復旧を実環境に近い試験で確認できる |

F1〜F3を最初の縦断として優先する。各段階の検証ではfixtureによる制御経路の確認と、実際のCoding Agent/SAAAによる意味理解・利用の確認を分けて記録する。

F5では、まず閾値判定や分類結果など具体的な利用要求から型を選ぶ。整数幅・overflow、欠損、文字列の符号化・長さ、配列上限、出力bufferの所有者を定義してからIRとABIを拡張する。一般的なループ・再帰・動的メモリを一括導入しない。

F6の初期設計では、Wasmが外部操作の提案を構造化データで返し、SAAA/ホストが権限を確認して実行する方式を優先する。直接のhost importが必要になったら用途ごとに導入する。現在のBunホストに将来の任意Wasmを安全に中断できる保証があるとは扱わず、隔離プロセスや適切な資源制御を選定・検証する。

## 7. 最初のPoC：利用者の受付判定を能力にする

新しい型やmemoryを足さず、現行のboolean・enum・存在判定で一巡を作る。

1. SAAAが「有効で、利用停止中でない利用者を受け付ける」能力を依頼し、入力契約と受け入れシナリオを保存する。
2. Coding AgentがSource、実装IR、部品テストを製造し、Wasmで検証して提出する。
3. SAAAが能力の説明と契約を読み、通常の呼び出し経路で受付シナリオを実行する。
4. 試験用に停止条件を欠いた候補を用意し、受け入れで拒否して修正依頼を返せることを確認する。この故障注入は、実モデルの誤り率の測定とは区別する。
5. 修正版だけを登録し、SAAAが利用可能機能として呼び出す。
6. 別版への更新、古い合格結果の流用拒否、配備失敗時の旧版維持、反復上限での停止を確認する。

初期adapterは構造化された依頼・応答と能力呼び出しAPIを定義し、Codex、pi、Nightworkersに固有の連携はその外側へ置く。SAAA実装の接続仕様がまだ入手できない場合、契約に従う模擬ホストで先行実装できる。ただし模擬ホストの成功を実SAAA連携の完了とは報告しない。

## 8. 現状との差分と実現見通し

現在は[Prompt Source実装計画](./PROMPT_SOURCE_IMPLEMENTATION_PLAN.md)と[評価結果](./PROMPT_SOURCE_EVALUATION_RESULTS.md)にある、制限されたPredicateのSource更新、意味解決、Lock、Wasm build/test/inspect、fixture評価が土台になる。汎用のテスト製造、SAAA受け入れ、能力レジストリ、自律修正ループは今後の実装対象である。

| 対象 | 現時点の見通し | 次に確かめること |
| --- | --- | --- |
| 能力パッケージ・二段階判定・版管理 | 高い。既存の成果物検証を拡張できる | 判定対象の取り違え、配備競合、旧版維持 |
| 制限Predicateでの製造・修正・配備の一巡 | 高いが、実エージェント接続は未確認 | 故障注入と実エージェント利用を分けた縦断試験 |
| エージェント生成テストで意味の誤りを十分に検出 | 中程度 | 同じ誤解の共有、未検証要求、反例の検出率 |
| SAAAが目的に合う能力を選び受け入れる | 中程度 | 説明の理解、呼び出し失敗、シナリオの判定品質 |
| 任意の自然言語から汎用能力を自律獲得 | 未判定 | 型・効果の対応範囲、仕様の曖昧さ、運用結果の蓄積 |

以上は設計上の所感であり、測定した成功確率ではない。評価では、誤配備、誤った候補の見逃し、正しい候補の過剰拒否、修正成功率、反復数、費用・時間を分ける。合格条件と予算は実行前に保存し、結果を見てから緩めない。

## 9. 従来計画の扱い

本書を、今後の機能拡張の優先順位とエージェント間の責務分担の基準とする。[旧Wasmコンセプト](./WASM_COMPILER_CONCEPT.md)の決定的コンパイル、制限profile、再現性は継承する。

独立した研究datasetや人間参加のA/B評価は、精度や開発時間短縮を研究結果として主張するための別工程である。その準備が未完でも、能力パッケージ、生成テスト、受け入れrunner、配備の実装は進められる。自動検証の結果を人間が毎回承認する運用は前提にしない。

人間への確認は、既存の会話・仕様・運用方針では決められない目的や権限が残った場合に限定する。実モデルのAPI利用条件や実SAAA接続に必要な情報は、必要になった段階で具体的に扱う。モデル精度が未評価であることを、全開発の停止理由にはしない。
