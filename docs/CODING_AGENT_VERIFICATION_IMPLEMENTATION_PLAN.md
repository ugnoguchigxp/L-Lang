# 次の実装計画：SAAA接続前の実装・テスト製造と修正検証

2026-09-15。状態：V1〜V5実装済み。基点は`da72a47`（`wasm-compiler`）。[能力パッケージの実装](./CAPABILITY_PACKAGE_RESULTS.md)に続き、Coding Agent側の製造・検証を整える。

## 1. 今回の目的と範囲

自然言語の仕様から実装とテストを別々に製造し、実際のWasmで検証する。さらに、テストが意図的な誤実装を検出できるかを調べ、不合格の候補を修正して同じ条件で再検証できるようにする。

SAAAの導入は後回しにする。実SAAAへの接続だけでなく、模擬SAAA、利用目的の受け入れrunner、能力レジストリ、配備処理も今回作らない。SAAA受け入れは引き続き`not-run`とする。

今回の入力は、入力契約と要求が整理された既存Prompt Sourceとする。自由な会話からの仕様作成、型や演算の拡張、任意コードの実行環境、複数エージェントの起動基盤まで一度に実装しない。現行の`predicate-i32-v1`と能力パッケージを利用する。

## 2. 現在できることと追加すること

| 項目 | 現状 | 今回追加するもの |
| --- | --- | --- |
| 実装の製造 | SourceからIR・Lock・Wasmを作れる | テスト製造と区別した依頼・成果物の記録 |
| テストの製造 | Coding AgentがJSON suiteを記述できる | 要求からsuiteを製造する構造化adapterと応答検査 |
| 部品検証 | Source例とsuiteをWasmで実行できる | 既存runnerを呼び出す一連の実行手順 |
| テストの検出力 | 手で用意した一つの誤実装を検出済み | 制限したIR変異の生成と、生き残った誤実装の報告 |
| 修正・再提出 | 個別コマンドで実行できる | 失敗から修正依頼を作り、固定したsuiteで1回だけ修正を検証する経路 |
| 再現・記録 | packageHashと部品検証reportがある | 製造時の応答、入力hash、試行履歴を保存し、モデルなしで再検証 |

目標は「Coding Agentが正しいと宣言すること」ではなく、何を作り、どのテストで何を検出し、修正でどう結果が変わったかを実行記録で確認できること。

## 3. 製造の契約

実装製造とテスト製造を別の構造化呼び出しにする。同じモデルを使う場合でも、一方の出力をもう一方の生成入力へ自動的に含めない。

テスト製造側にはSource revision、intent、要求IDと文章、入力契約、未解決条件、profileを渡す。実装IR、Lock、Wasmの結果、既存Source例、評価用の非公開ケースは渡さない。応答は`generated`、`unresolved`、`error`を区別し、generatedの場合は既存CapabilitySuiteへ変換・検査する。sourceRevisionは呼び出し側で照合し、モデルに対象版を自由に選ばせない。

実装製造側は既存のresolverを再利用する。生成したsuiteは初回実装のモデル入力へ渡さず、生成後の検証に用いる。構造化出力の成功だけでは合格にせず、既存の型・IR・Source例・実Wasm検証を通す。

テスト生成の結果がSource例と同じ入力に異なる期待値を付けた場合は、テスト仕様の矛盾として停止する。欠損と明示的undefinedを区別して入力を比較する。実装に合わせた期待値への自動変更は行わない。矛盾が見つからないこと自体は、自然言語の正しさの証明にはならない。

不正schema、要求ID欠落、空suite、過大入力、拒否応答を診断として残す。要求対応だけを増やして、テストが十分だとみなさない。テスト製造の未解決は実装不良とは区別する。

## 4. テストの検出力を調べる最小機能

合法なPredicate IRに対して、次の変異だけを作る。

- `all` / `any`の条件を一つ取り除く。ただし合法なIRを保つ場合に限る。
- `all`と`any`を入れ替える。
- 条件を否定する、または既存の否定を取り除く。
- booleanの比較値を反転する。
- enumの比較値を契約にある別の値へ変える。

変異ごとに対象IR位置、操作、元・変更後IR hashを保存する。重複する変異を除外し、最大32変異とする。どの変異を選ぶかは決定的な順序で固定し、未実施数も残す。

有限な観測状態を4096通りまで列挙し、元IRと変異IRに差がある入力を探す。現行profileで文字列の中身を観測しない箇所は、存在状態の代表値として扱う。これはそのprofileのIR上の比較であり、任意文字列や将来の演算に対する全入力の証明ではない。入力adapterには別に空文字・通常文字列・欠損などの試験を残す。

結果は、検出済み、未検出、同値、判定上限超過、実行エラーに分ける。元IRと異なる結果を返す反例がある変異だけを、非同値と確定する。同値をテスト失敗として数えず、上限超過を同値とも扱わない。

まずSource例で検出された変異と、追加suiteで初めて検出された変異を分ける。Source例に反する変異は通常のLock検査で止まるため、「suiteがWasmで検出した」とは報告しない。残る変異は公開用Lockや候補を書き換えず、隔離した試験用成果物としてコンパイル・実行する。既存の公開候補の検証を迂回するオプションは追加しない。

元IRの出力は変異の同値比較にだけ用い、自然言語に対する正解やsuiteの期待値には転用しない。変異検査はテストの弱点を見つける補助であり、意味の正しさを保証する認定にはしない。

## 5. 修正は1回に限定する

初回の部品検証で実際の期待値不一致が出た場合、失敗した要求ID、入力、期待値、実際の結果、候補hashを含む修正依頼を作る。実装側へ元の仕様と失敗ケースを渡し、新しいIR候補を受け取る。

Source、入力契約、元の例、生成suiteは初回の検証前に固定する。修正でそれらを変更しない。検証条件の変更が必要なら別の仕様変更として停止理由を出す。

現在のresolveは有効なLockを再利用するため、同じファイルでresolveを繰り返しても修正にはならない。各試行は同一Sourceを持つ新規ディレクトリで製造し、既存Lockを削除・上書きしない。元の候補と修正版のpackageHashをそれぞれ保存する。

修正版を同じSource例とsuiteで検証し、pass/fail/errorを記録する。修正が不成功、未解決、不正IR、同一IRの再提出、上限到達なら停止する。ファイル不整合やランタイム障害を、自然言語の修正依頼で解消しようとはしない。変異の未検出だけを理由に仕様やテストを自動書き換えするループも作らない。

自動修正は最大1回、モデルへの論理呼び出しはテスト製造・初回実装・修正の最大3回とする。通信層の暗黙retryは使わず、失敗も消費済み呼び出しとして記録する。汎用のPDCA制御は後続へ分離する。

## 6. 実行記録とCLI案

実行開始時に、Source・metadata・実行設定のsnapshotを新規runディレクトリへ保存する。生成後のsuiteを固定し、そのhashを以後の試行に結び付ける。各段階の入力・応答、使用adapter、モデル識別情報・token usage、候補hash、部品report、変異report、停止理由を記録する。途中終了を完了と取り違えないよう段階ごとにcheckpointを残す。

例示するコマンドは新設案であり、現在は利用できない。

```text
capability develop <source> --metadata <file> --fixtures <responses> --out-dir <new-run>
capability mutation-check <package-manifest> --report <new-report>
capability replay-development <run-directory> --out-dir <new-run>
```

developはテスト製造、初回製造、部品検証、必要なら1回の修正を実行する。mutation-checkはテストの検出力を別reportとして評価する。replay-developmentは保存済み応答から再構築・再検証し、モデルを呼ばない。replayによる新規ビルドにはコンパイラが必要だが、既存のcapability verifyは引き続きコンパイラ不要とする。

新規APIは依頼・応答・run記録をstrict schemaで扱う。既存Capability Manifest/reportにSAAA合格状態を追加しない。結果は「部品検証の成否」「テスト検出力」「試行の完了・停止」を別々に返す。変異の未検出を隠して単一の成功率へまとめない。

## 7. 実モデルとfixtureの扱い

StructuredAgentと既存モデル接続を再利用するテスト製造・修正adapterを実装する。CLIのlive実行ではmodel、出力token上限、総token上限、総実行時間上限を必須とし、各呼び出しの前に残量を確認する。最大入力と最大出力の保守的な上限で予算を予約できない場合は呼び出さない。usage不明・超過は以後の呼び出しを停止する。金額換算を扱う場合は料金設定の版と事前上限も必要とし、token数だけを金額保証とは呼ばない。

今回の開発・CIはfixtureとmockで完結させる。有料実行や人間の都度レビューを実装の前提にはしない。実モデルの試行は実行条件が決まった段階で同じ経路から行い、fixture結果とは分けて報告する。

fixtureは成功・失敗・修正の制御を試すためのもの。実モデルのテスト生成品質や修正成功率は、それを実際に実行するまで未評価と明記する。Codex、pi、Nightworkersのプロセスを起動・管理する製品別連携は今回含めない。

## 8. 実装順序と受け入れ条件

| 段階 | 実装 | 受け入れ条件 |
| --- | --- | --- |
| V1 | 製造依頼・応答・run記録のschema、入力snapshot、段階別checkpoint | 不正入力と古い応答を拒否し、途中runを完了扱いしない |
| V2 | 要求からsuiteを作るadapterと検査 | 実装・既存例を生成入力へ漏らさず、矛盾・未解決・不正suiteを区別する |
| V3 | 既存実装製造とpackage/verifyへの接続 | 実装とsuiteを別々に製造し、実Wasmの部品検証結果を保存できる |
| V4 | 制限した変異検査とreport | 非同値の未検出変異を報告し、同値・未判定・エラーを区別する |
| V5 | 1回の修正とoffline replay | テストを変えずに修正版を検証し、失敗・上限到達で停止、保存済み応答から再検証できる |

修正先の目安は新規のcapability-development、capability-test-agent、capability-mutationと既存CLI。prompt-agent、prompt-resolution、capability-package、capability-testsの責務を再利用し、大規模なディレクトリ再編成は行わない。

## 9. 最小の検証課題

1. **受付判定**：有効かつ非停止なら許可する。停止条件を欠く初回候補をsuiteで検出し、同じsuiteで修正版を合格させる。
2. **区分と存在判定**：premiumかつメール項目が存在する場合に許可する。現行仕様では空文字は存在する。null、undefined、欠損は契約に従って区別し、解釈違いを検出する。
3. **論理条件**：AND・OR・NOTを含む要求を使い、演算の入れ替えや条件の欠落が検出できるか確認する。

各課題に、開発用の正解・既知の反例を生成入力と別に用意する。これはエージェントの自己評価を照合する小規模な開発fixtureであり、独立した研究評価datasetとは呼ばない。

意図的に弱いsuiteが部品テストを通っても、非同値の変異を見逃していることを報告できるようにする。重複条件の削除など同値変異も含め、すべてを検出すべき誤りとして数える実装を防ぐ。

失敗試験には、suiteの期待値改変、修正による指定外変更、Source/応答/hash不一致、候補衝突、モデル拒否、usage不明、予算不足、同一IRの再提出、途中終了、Worker timeout、列挙上限超過を含める。

## 10. 完了判断と次の段階

fixtureによる3課題の製造・検証、既知の弱いテストの検出、1回の修正成功と停止経路、API呼び出し0回のreplayを再現できることを完了条件にする。既存のformat、lint、typecheck、coverage、CLI smoke、protected inputs、Markdownリンクと3 OS CIを通す。

結果文書には、作った候補、固定suite、検出できた誤り、見逃し、同値・未判定の変異、修正の成否、呼び出し回数と費用の測定範囲を記載する。新規機能があることと、実モデルが高い精度で使えることを分けて報告する。

この段階を終えてもSAAA導入へ自動着手しない。実モデルでの製造品質や、具体的な処理に必要な型・演算の不足を確認したうえで、SAAA検証へ進む時期を改めて決める。
