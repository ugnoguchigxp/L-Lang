## 1. このブランチで目指すこと

L-Langで確定した意味をWebAssemblyへコンパイルし、生成した`.wasm`をアプリケーションから読み込んで実際に利用できるようにする。

最初の到達点は、現在のBoolean Predicateを対象に、意味の検証、Wasm生成、保存、読み込み、呼び出し、結果の確認までを一つにつなぐことである。Wasmファイルを出力するだけでは完了としない。

その先に、人間が自然言語で要求を伝え、LLMが正式なソースであるPrompt Sourceを保守し、検証可能なIRと決定的なコンパイラを通じて実行物を作る言語基盤を目指す。

本書は、提案文書「L-Lang 次期アーキテクチャ実装指示書」の方向性を、現行実装との比較・評価を踏まえて整理したものである。元文書の全フェーズを一括で実施する計画ではない。

## 2. 現行コンセプトとの関係

[既存コンセプト](../concept.md)と[現行ロードマップ](../PROJECT_STATUS_AND_ROADMAP.md)は、TypeScriptを基盤とした研究MVPを説明している。本書はその実装状況を上書きせず、次の発展方向を定める。

継承する中心価値は、抽象的なIntentをプロジェクトの型・契約・検証済み文脈へ適合させ、実行時にLLMを必要としない処理へ具体化することである。

将来はTypeScriptの表面構文やコード生成を中核の前提から外す。ただし、移行中は既存のTypeScriptバックエンド、テスト、Lock、replayを比較・回帰検証に利用する。Wasmを標準バックエンドへ変更する判断は、利用可能性と測定結果を確認した後に行う。

現行の[Predicate IR](../src/ir.ts)には`all`、`any`、`not`、`equals`、`present`があり、[Semantic Lock](../src/semantic-lock.ts)には解決済みIR本体が保存されている。[コンパイラ](../src/semantic-compiler.ts)にもLLMを使わないreplay経路がある。これらを出発点とし、再現性の仕組みをゼロから作り直さない。

初期Wasm経路では、旧Lockの整合性確認に限り既存TS rendererの内容hashを照合する。TSファイルやTS実行をWasm生成の中間成果物にしない。将来のResolution Lockでは、この旧バックエンド依存をIRの独立した整合性検査へ置き換える。

## 3. 長期的な処理モデル

```text
人間の要求・変更指示
  ↓ Source Agent
Prompt Source + 型・契約・プロジェクト文脈
  ↓ 明示的な意味解決（LLM）
Candidate Semantic IR
  ↓ 構造・型・制約の検証と受け入れ条件の評価
Resolved Semantic IR / Resolution Lock
  ↓ 決定的なlowering
Typed Core IR
  ↓ ABI・配置の決定
Wasm + Build Manifest
  ↓ ホストによる入力検証・変換・読み込み・呼び出し
アプリケーションで利用
```

LLMは要求の構造化、意味に対応する合法なIR操作の選択、曖昧さの検出を担当する。物理ABI、メモリ配置、解放処理、バックエンド命令列はコンパイラが決定する。LLMにRaw Wasm、WAT、LLVM IRを直接生成させる構成は採らない。

Source更新、意味解決、決定的ビルドは独立した操作とする。Sourceや型環境が変わってLockが古くなった場合、通常ビルドは理由を示して失敗し、暗黙にLLMを呼び出さない。Agentが後続操作として意味解決を起動する場合も、この境界を維持する。

## 4. Prompt Source

Prompt Sourceは、LLMがスキーマに従って生成・更新する、自然言語を中心とした正式な意味記述である。人間向けの新しい関数構文を作ることは目的にしない。

最小構成は、版、Concept ID、Intent、入力・出力契約、識別子付き要件、解決不能条件、実行制約、検証例とする。将来は依存Concept、properties、Capability、失敗方針などを拡張する。

要件は必須条件・禁止条件・希望条件に分け、希望条件を満たせないことと必須条件違反を混同しない。実装ヒントは契約を上書きできない。自然言語のinvariantは、記述されているだけでは証明済みとして扱わない。

Source Agentの読み書きAPIはスキーマ検証を行い、安定した要件IDと更新前revisionによって局所更新・競合検出を支える。元の要求と更新内容の対応を残し、LLMの内部推論過程は保存しない。

物理保存形式は当初canonical JSONを候補とする。形式の最終判断は生成成功率、トークン量、再読込、局所更新時の要件保持率で行う。表現形式の比較を最初のWasm動作確認の前提にしない。

## 5. 正しさと保証の境界

次の四つを別々に検証し、結果を記録する。

| 検証対象 | 確認方法 | 限界 |
| --- | --- | --- |
| 要求から意味への適合 | 独立した期待結果、受け入れ例、変更課題、未解決判定 | 自然言語の完全な正しさを型検査では証明できない |
| IRの合法性 | Schema、型、操作、効果などの検査 | 合法なIRでも要求を誤解している可能性はある |
| loweringの意味保持 | 参照interpreter・既存バックエンドとの比較、有限領域の全列挙 | サンプリングテストの成功は全入力の証明ではない |
| 実行境界 | Wasm validation、ABI入力検証、export/import契約の検査 | ホストやランタイムを含む全障害を排除するものではない |

要件IDとIR・検証結果の対応を追跡し、「形式的に検証済み」「テストで確認済み」「未解決」を区別する。LLMが生成したテストだけを要求適合の独立した証拠としない。判断材料が不足する場合は`unresolved`を返す。

人間による生成コードのレビューを通常の必須工程にはしない。これは要求の妥当性を確認する必要がなくなることを意味しない。自動承認も、明示した受け入れ条件と検証記録に基づく。

`total`は受理した入力契約の範囲で停止し、定義された結果を返す性質とする。ホスト側での不正入力拒否、ランタイムの資源不足、プロセス障害は別に扱う。将来の再帰・ループ・外部呼び出しへ同じ保証を無条件に広げない。

## 6. IRと意味の仕様

Semantic IRは要求を具体的な操作へ解決したもの、Typed Core IRは型付きの実行操作、ABIはホストとの物理的な受け渡し規則を表す。最初から大規模なSSA基盤やMLIR Dialectを作らず、Predicateに必要な表現から始める。

バックエンド追加に先立ち、次を明文化する。

- `all` / `any`の評価順序と短絡評価
- `equals`の型別の意味
- `present`と欠損・`null`・`undefined`の関係
- 不正なproperty pathと入力値の扱い
- enumのtag割り当てと不正tagの拒否
- 将来追加する数値の幅、overflow、NaN、符号付きゼロの扱い

構想時点では[TypeScript生成器](../src/generator.ts)の`===`と[benchmark evaluator](../src/cross-schema-benchmark.ts)の`Object.is`で、`-0`と`0`の比較が一致しなかった。初期PoCのP0でevaluatorをstrict equalityへ統一し、回帰テストを追加した。現行IRは非有限数リテラルを拒否しているため、NaNを含む将来仕様と現在の再現可能な不一致を区別して整備する。

Canonical Type IRは将来の中核とし、TypeScriptの型抽出はType Providerの一つへ分離する。ただし、TypeScriptの`number`を根拠なく整数へ変換したり、`null`と`undefined`を区別する既存契約を単一optionへ機械的に潰したりしない。

## 7. 最初のWasm縦断

対象は[既存のactive-customer](../examples/active-customer/semantic.ts)と同じ契約とする。

- `status`が`active`
- `deletedAt`が`null`
- `email`が`null`でも`undefined`でもない
- 空文字のemailは「存在する」として受理する

最初のABI案は次の通り。名前とtag値は実装計画で固定する。

```text
is_active_customer(
  status_tag: i32,
  deleted_at_is_null: i32,
  email_present: i32
) -> i32
```

ホストadapterは入力契約を検証し、enumと存在状態をABIへ変換する。顧客の適格性をホストで事前計算せず、条件の組み合わせはWasm側で評価する。ABIのboolean値は0/1、enumは宣言済みtagに限定する。

この経路ではbool、closed enum、存在タグ、recordのflatteningに範囲を限定し、生成モジュールにlinear memory、heap、GC、RC、外部importを必要としない。i64、浮動小数点、任意文字列の比較は初期縦断の前提にしない。対象外のIR・型は明示的に拒否する。

参照を持たない段階ではownership操作そのものを禁止し、一般的な借用検査器の完成を待たない。

## 8. 生成物を利用する体験

利用者が手書きのWATやTypeScriptの判定関数を用意せず、次の操作を行えることを目指す。

1. 検証済みのResolutionから`.wasm`とABI・provenance情報を生成する。
2. 保存した成果物を別の実行プロセスで読み込む。
3. ホスト用APIで入力を渡し、boolean結果を受け取る。
4. 同じinstanceを複数の呼び出しで再利用する。
5. Source不整合、成果物不整合、不正入力を区別して診断する。

初期ホストは現在のプロジェクトで使うBun/TypeScriptとする。これは呼び出しadapterであり、PredicateをTypeScriptへ生成して実行する迂回経路ではない。ランタイム利用時にはLLM・コンパイラ・Binaryenを不要にする設計を目指す。

初期CLI/APIの名称は未確定であり、既存コマンドとの関係を実装計画で決める。ブラウザや他言語ホストへの対応は後続段階とする。

## 9. Lock、ビルド情報、再現性

既存の解決済みIR・入力hash・replay検証を引き継ぎ、次の責務を分離する。

| 記録 | 内容 |
| --- | --- |
| Resolution Lock | Source、型環境、意味に影響する文脈・依存のhash、解決プロトコル、解決済みIR本体、モデル識別情報 |
| Build Manifest | IR hash、コンパイラ・バックエンドの版とオプション、ABI版、target features、成果物hash |
| 検証記録 | 対象の要件・入力・IR・成果物、検証器の版、検査とテストの結果 |

同一Resolutionと同一ツールチェーン・設定から、同一Wasm bytesを生成できることを目指す。日時、絶対パス、非決定的な列挙順をバイナリへ混入させない。異なるコンパイラ版でのバイナリ一致は要求せず、意味保持を別に検証する。

意味の再利用と、検証結果の再利用を分ける。検証器や受け入れ条件が変わった場合、IRを再利用できても検証は再実行し得る。

Lockに必要なIRやSourceを、LRUで削除されるキャッシュだけに保存しない。Wasmをportableな配布成果物とし、最適化・AOT成果物は再生成可能な派生成果物として扱う。キャッシュを導入する段階で容量上限と削除方針を定める。

## 10. GC-Free Safe Profileの発展

初期保証の対象は生成されたpredicateの実行であり、JavaScriptホストやWasmのコンパイル・初期化を含むプロセス全体のGC不要・メモリ確保不要を意味しない。

将来はvalue、call-scoped borrow、unique、slice、region、resource handleを段階的に検討する。必要になった時点でmove後の使用、borrowのescape、alias、二重解放、未初期化アクセスを検証する。

Wasmのlinear memory境界検査だけでは、個々のオブジェクト境界や寿命の安全性は保証されない。メモリを導入する段階では、L-LangのVerifierとホスト契約でその範囲を補う。

文字列をUTF-8 sliceで受け渡す場合も、通常のJavaScript文字列からの変換やコピーが不要になるとは限らない。メモリの所有者、寿命、encoding、出力bufferをABIに定義する。

## 11. バックエンドと性能評価

Direct Wasm emitterはBinaryen.jsを第一候補とする。外部assemblerやCargo・LLVM・MLIR・CMakeを通常ビルドの必須依存にしない。初期化時間や依存サイズが問題かを測ってから、独自encoderの必要性を判断する。

計測は、意味解決、backend初期化、lowering、Wasmコンパイル、instance生成、入力変換、単発呼び出し、繰り返し・batch実行、RSS、成果物・cache容量に分ける。TypeScript版と同じ入力・処理で比較し、ABIコストを除いた数値だけで高速化を主張しない。

Wasm最適化とWasmtime AOTは実測後の候補、QBEはNativeが必要な場合の実験、MLIR/LLVMは高度な最適化が必要な場合の研究経路とする。どれも初期ブランチの完了条件には含めない。

## 12. 段階的な到達点

| 段階 | 到達点 | 次へ進む判断材料 |
| --- | --- | --- |
| A：意味とbaseline | 現行挙動、equality、入力契約、比較用の期待結果を固定 | 既存の不一致・CI失敗と追加変更の影響を区別できる |

## 13. 初期縦断の受け入れ条件

- 対応範囲の検証済みPredicate IRから、TSコード生成を介さずWasmを生成できる。
- 保存したWasmを別プロセスで読み込み、ホストAPIから既存active-customer契約を実行できる。
- 有効なenum・存在タグの有限な組み合わせを全列挙し、独立した期待結果と一致する。
- 元のCustomer入力から結果までのadapterを含むテストで、空文字、欠損、null、不正enumを確認する。
- 不正IR、未対応型・操作、不正ABI値を拒否する。
- Wasm構造検証に成功し、初期profileに不要なmemory・importを持たない。
- 同じinstanceを繰り返し利用し、呼び出し間で状態が漏れない。
- 同一Lock・ツールチェーン・設定からのWasm bytesが一致する。
- 通常ビルド・実行にLLM呼び出しが不要で、古いLockは暗黙に解決し直さない。
- 最小のprovenanceを辿れ、コンパイル・実行・入力変換の測定値を記録する。
- 既存TS経路と関連する回帰検証を維持し、未解決のbaseline失敗を成功と報告しない。

PromptSourceのAgent API、一般的なownership checker、LRU cache、AOTは、この初期縦断の必須条件に含めない。

## 16. 現時点の評価と実現確度

### 16.1 評価の前提と総評

評価日：2026-09-14。以下はコンセプト、現行コード、既存の公式資料を基にした設計レビュー上の所感である。このブランチでWasmコンパイラを実装・実行した結果ではなく、工数・納期・成功率の実測もまだない。

総評は「初期縦断は実装へ進める。長期構想は段階ごとに確認しながら育てる価値がある」である。少数の型と論理操作をWasmへ落とす部分には、現時点で原理的な障害は見当たらない。難所はWasm命令の生成そのものより、入力の意味を失わないABI設計、既存のLock・型検査との接続、自然言語の変更を正しく反映し続ける仕組みにある。

確度は次の意味で用いる。数値の成功確率は、校正できる実績がないため付けない。

- **高い**：限定した条件では既存技術と現行実装の延長で到達を見込める。主な不確実性は実装と統合にある。
- **中程度**：成立する設計は描けるが、意味の保持や運用など、結論を左右する未検証の仮説がある。
- **未判定**：必要な比較・測定がなく、実装可能性から価値や優位性を推定できない。

いずれも無期限・無制限の開発を仮定した評価ではない。初期範囲を維持し、既存基盤を再利用する前提である。複数の「高い」を足し合わせて、長期構想全体の成功確率とはしない。

### 16.2 項目別の見立て

| 対象 | 現時点の確度 | 根拠と所感 | PoCで確かめること |
| --- | --- | --- | --- |
| 限定PredicateからWasmを生成する | 高い | 論理演算、enum比較、存在タグに絞れば、少数の整数・制御操作で表現できる。既存の構造化IRを使える | 一つの式の手書き変換で終わらず、対応範囲内の異なるIRを同じlowering経路で生成できるか |
| 保存したWasmをホストから利用する | 高い | 通常のWasm読み込み・export呼び出しの範囲に収まる。特別な独自ランタイムを必要とする構想ではない | 別プロセスでの読み込み、API型、エラー、instance再利用、コンパイラ依存の分離 |
| 初期predicateのGC・RC・heap不要 | 高い | 参照・memory・importを持たない値だけの処理に限定できる。汎用メモリ管理の完成を待たず成立する | 出力モジュールの構造と呼び出し経路が実際に制限を守るか。ホストの確保量とは分ける |
| ABI変換を含む意味保持 | 高い。ただし最優先の検証箇所 | 初期契約の状態を有限個のtagへ写せる。一方、変換で情報を失うとWasm内部が正しくても結果は誤る | null・undefined・空文字・不正入力と短絡評価。独立した期待結果との一致 |
| 決定的buildとLLM不要の再生成 | 高い | 現行LockにIR本体と入力hashがあり、replayもある。固定したemitterと設定で発展させられる | 別プロセスでのbytes一致、stale検出、版・設定変更時の無効化、旧経路の回帰 |
| PromptSourceの保存・API・schema検証 | 高い | 型付きデータとrevisionを扱う通常の実装として構成できる | 不正入力拒否、競合検出、canonicalization。これだけで意味の正しさを達成したとはしない |
| LLMによるPromptSourceの局所更新と意味解決 | 中程度 | 制限IRと要件IDは検査しやすいが、Source化とIR化の二段階で誤解が生じ得る | 複数回の変更後も無関係な要件が残るか、曖昧な要求を誤って確定しないか |
| レビューを通常工程に置かない運用 | 中程度。限定領域が前提 | 独立した受け入れ条件がある狭い領域なら成立を見込める。任意の自然言語要求の自動保証までは見込まない | 誤った候補が検証を通る頻度、過剰なunresolved、復旧手順、期待結果の独立性 |
| Type ProviderとCanonical Type IRの拡張 | 中程度 | 抽象化は可能だが、TS・OpenAPI・DBの型が同じ意味とは限らない | 欠損、nullable、整数幅、制約の対応。不明な差を拒否できるか |
| borrow・region等を含むGC-Free profile | 中程度 | 制限を保てば設計可能と考える。ただし所有権検査とホスト境界は新たな開発領域になる | 最小slice処理で寿命・alias・bounds・出力bufferを検証。初期のmemoryなしPoCから一般化しない |
| TypeScriptより高速・省メモリになる | 未判定 | 単純なpredicateでは入力変換や呼び出し境界が支配的になり得る。Wasm化だけでは優位を予測できない | 同じ仕事について単発・batch、cold・warm、adapter込みの時間とRSSを比較 |
| LLMによる直接コード保守より使いやすい | 未判定 | 再現性・制約には利点を期待するが、Sourceの追加管理や制限が負担になる可能性もある | 同じ変更課題の総時間、追加指示量、意図しない変更、復旧時間、費用 |
| QBE・MLIR等の追加が必要になる | 未判定 | 技術候補としては整理できるが、現段階で解決すべき実測上の問題がない | Wasm経路では満たせない具体的な用途・性能要件があるか |

### 16.3 PoCで確認しながら進められる理由

この構想は、後段の成功を待たず前段だけで評価できる。Wasm縦断には既存の解決済みIRを使えるため、Prompt Sourceの更新精度を先に解決する必要がない。逆に、Prompt Sourceの価値は既存interpreterでも評価でき、Wasmの性能改善を待つ必要がない。

したがって、最初のPoCで分かるのは「L-Langの確定した意味を、TS生成に依存せず利用可能な実行物へ運べるか」である。ここが成立すれば、実行形式を分離する設計の見通しは強くなる。ただし「LLMが意図を正確に保守できる」「開発が速くなる」「所有権を安全に扱える」という別の仮説は、それぞれ追加の証拠が必要である。

最初のactive-customerは有効なABI状態が2種類のstatusと二つのbooleanで8通りになり、全列挙しやすい。ただし8通りの成功が示すのは、その契約と式についての結果である。コンパイラ全体を評価するには、`all`、`any`、`not`、`equals`、`present`の異なる組み合わせを追加し、adapterにも元の入力値を使った独立した検査を行う。

### 16.4 PoCごとの継続・見直し条件

| 確認点 | 進めてよい証拠 | 期待を満たさなかった場合 |
| --- | --- | --- |
| Wasm縦断 | 保存物を別プロセスで実行でき、対応操作・独立した期待結果・不正入力拒否を確認できる | emitter、ABI、loweringのどこに問題があるか分離する。命令を手書きした一例だけで完了としない |
| 意味保持 | 有限状態の全列挙、複数IR、adapterを含む検証で結果が一致する | 型や操作の対応範囲を狭め、表現できない要求を拒否する。期待結果を出力に合わせて変更しない |
| 再現性 | 固定条件で別プロセスの成果物が一致し、入力変更はstaleとして検出される | 非決定的なmetadataや依存を特定する。原因不明のまま再現性を主張しない |
| 性能 | 選んだ利用場面の実用上の時間・容量条件を満たす | TSより遅いだけで構想全体を棄却せず、配布・分離の価値も評価する。実用条件を満たせないなら標準化を延期する |
| Sourceの継続更新 | 凍結した変更課題で、要件保持・期待結果・未解決判定を確認できる | 更新単位や対応領域を狭める。誤解の問題をバックエンド追加で解決しようとしない |
| メモリprofileへの拡張 | 具体的な用途があり、最小例で寿命・境界・alias違反を検出できる | memoryなしprofileを維持する。汎用profileの未達は初期Wasm経路の失敗と区別する |

性能やSource更新の合格閾値は、この所感から都合のよい数字を作らない。探索用の測定で利用場面と予算を決め、その後の評価用課題と閾値を結果を見る前に固定する。

### 16.5 現時点で補強したい設計

以下は構想を止める問題ではなく、実装計画の最初で決めておきたい点である。

1. **ABIが失ってよい情報を定義する。** `email_present`は存在判定には十分だが、後に文字列比較を追加すると不十分になる。IRが必要とする観測情報からABIを決め、ABI変更を版・hashに反映する。
2. **入力保証の入口を明示する。** 生のWasm exportは直接呼べるため、adapterでの検証を迂回できる。初期の保証は「検証済みホストAPIを通した入力」に対して成立させるか、Wasm側にも拒否処理を持つかを決める。
3. **実行時の成果物検証を定義する。** 配布先にSourceがない場合でも、WasmとManifestの組み合わせ・ABI版・export署名を確認できるようにする。hash一致は組み合わせの整合性を示すもので、配布者の真正性まで示すものではない。
4. **初期PoCでも汎用の変換経路を保つ。** 顧客のフィールド名や期待結果をemitterに埋め込まず、型とIRから生成する。別の対応Predicateを追加する際にemitterの条件分岐を増やさずに済むかで確認する。
5. **現行の既知問題を先に記録する。** equalityの不一致と既存CIの失敗状況をbaselineで確認し、PoCの不具合・未検証と混同しない。
