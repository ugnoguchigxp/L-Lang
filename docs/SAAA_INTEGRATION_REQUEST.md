# SAAA側への開発依頼：S-LANG能力の受け入れ・配備PoC

> 分類：記載された基点に対する外部接続依頼・計画です。外部SAAAの現在の実装状態を保証するものではありません。提供済みR1キットは[操作例](../examples/saaa-host/README.md)を参照してください。キットはCapability v1向けで、JSONC Capability v2は現行`capability:host`の対象外です。

2026-09-16。依頼元：S-LANG（リポジトリ名L-Lang）。対象基点：`wasm-compiler`の`2d31e9e`。本書はSAAA側の開発担当・Coding Agentへ渡す依頼書であり、連携が実装済みであることを示すものではない。

## 依頼したいこと

SAAAがユーザーとの会話から不足する能力を整理し、Coding Agentへ製造を依頼し、届いたWasm能力を自分の通常のスキル呼び出し経路で評価する機能を実装してください。合格した候補だけを利用可能な能力として登録し、不合格なら再現情報を付けて修正を依頼してください。

最初の対象は「有効かつ利用停止中でない利用者を受け付ける」という、副作用のないboolean判定です。能力の取得、受け入れ失敗、修正、再検証、ローカル配備、通常利用、旧版への切り戻しまでを一巡させます。毎回の人間によるコードレビューや配備承認は必須にしません。意図や権限が既存の方針で決まらない場合だけユーザーへ確認します。

先行していた「SAAA導入を後回しにする」方針は、今回の依頼により導入計画の段階へ進めます。SAAAの実装構成はこのリポジトリから確認できないため、以下の操作名は論理的な契約案です。既存のtool/skill、ジョブ、永続化、権限管理に合わせて実装してください。特定のHTTP APIや新しいエージェント基盤を必須にはしません。

## 責務の境界

| 担当 | 今回の責務 |
| --- | --- |
| SAAA | 目的・要求・受け入れ条件を固定し、製造を依頼する。能力の発見、入力作成、出力の解釈を含む利用検証を行い、配備・無効化・切り戻しを決める |
| Coding Agent | 自然言語仕様から実装と部品テストを別々に製造する。実Wasmで検証し、候補と実行記録を提出する。修正時にも再検証する |
| S-LANG | Source/Lock/Wasm/テストの整合性、入力契約、部品検証を担保する。SAAA接続に必要な呼び出しadapterと修正入力の不足を補う |
| SAAAのホスト・レジストリ | 登録済みの版を解決し、制限内で実行する。二段階の合格と対象hashを確認して原子的に有効版を切り替える |

Coding Agentには受け入れ条件・SAAAの合格記録・有効版を書き換える権限を与えません。SAAAは部品テストの期待値を書き換えて候補を通しません。共有フォルダのファイル名だけで権限を分離したことにはせず、配備操作の入口で検査します。

## S-LANG側で現在できること

[実装結果](./CODING_AGENT_VERIFICATION_RESULTS.md)と[操作例](../examples/capability-development/README.md)が現行仕様です。

- `capability package / inspect / verify`で、能力パッケージの作成、整合性確認、実Wasmによる部品検証ができます。
- `capability develop`で、テスト製造、実装製造、最大1回の部品テスト失敗修正ができます。最大3回の論理呼び出しとtoken・時間上限を設定します。
- `mutation-check`はテストの見逃しを検査し、`replay-development`は保存応答からAPI呼び出しなしで再構築・比較します。
- profileは`predicate-i32-v1`、出力はboolean、`permissions: []`です。boolean、enum、存在判定と論理演算を対象にします。数値計算、任意の文字列処理、配列変換、外部API操作は今回の対象外です。
- 部品検証reportは`status: pass | fail | error`を持ち、`acceptance`は常に`not-run`です。これをSAAAの合格に書き換えてはいけません。

実モデルの生成品質は未評価です。これまでの製造・修正試験はfixtureとローカルの模擬APIによるものです。既存Workerの10秒timeoutはありますが、任意の外部Wasmに対する完全な隔離を保証しません。今回は信頼するローカル製造経路が作った制限profileの成果物だけを扱います。

既存の`develop`はCodex/pi/Nightworkersなどのプロセスを起動・管理する仕組みではありません。また、SAAAからの受け入れ失敗を読み込んで固定suiteを引き継ぐ修正CLIは未実装です。部品テスト内の1回の修正と、今回追加するSAAAからの修正依頼を区別してください。

## 最初の利用シナリオ

1. ユーザーが「有効で、利用停止されていない利用者だけを受け付けたい」と伝える。
2. SAAAが要求ID、入力契約、boolean出力の意味を確定し、候補を見る前に受け入れシナリオを保存する。
3. Coding Agentが候補一式と部品検証結果を提出する。
4. SAAA側が候補を再検証し、試験用の名前空間へ読み込む。この時点では通常利用へ公開しない。
5. SAAAが自然言語のタスクから能力を選び、入力を作り、ホスト経由で呼び出し、結果を解釈する。機械判定でシナリオの合否を記録する。
6. 失敗なら修正依頼を返す。修正版は別のpackageHashとして再検証する。
7. 合格版だけを通常の能力一覧へ登録し、別の会話タスクから再び発見・呼び出しできることを確認する。
8. 更新失敗時は旧版を維持し、配備後の問題では無効化または旧版へ切り戻す。

受付判定の真理値表は以下です。入力のboolean値を文字列や推測値から暗黙変換しないでください。

| enabled | suspended | 期待値 |
| --- | --- | --- |
| true | false | true |
| true | true | false |
| false | false | false |
| false | true | false |

必須入力欠損や型不一致は実行エラーです。正常な`false`（受付不可）と区別して上位へ返してください。SAAAが「受付した」と説明しても、Wasmを呼んだ記録がなければ成功とは判定しません。今回の能力は受付可否を返すだけで、外部システムへの受付登録は行いません。

## 連携契約案：既存成果物の外側に追加するもの

以下は新規の連携仕様案であり、既存CLIがこのJSONを直接受理するわけではありません。着手時に双方でschemaを固定し、不明な版や不正な値は拒否してください。

| 記録・操作 | 必須情報・振る舞い |
| --- | --- |
| 製造依頼 `request` | protocolVersion、requestId、要求revisionとhash、目的、要求ID一覧、入力契約、出力、profile、利用範囲、予算、期限、修正上限。既存Prompt Sourceとmetadataへ変換する |
| 候補提出 `candidate` | requestId、要求hash、candidateId、packageHash、候補一式の保管参照、部品検証report、製造run・変異reportの参照または未実行理由。参照だけを信用せず受信側で整合性を検査する |
| 受け入れ計画 `acceptance-plan` | planId、revision、hash、要求hash、シナリオID、タスク入力、期待する能力選択・呼び出し・出力解釈、機械判定条件、時間上限。SAAA側で候補提出前に固定する |
| 試験呼び出し `invoke` | requestId、invocationId、候補または登録済み能力IDとpackageHash、入力、期限。JSONで明示的undefinedが必要なら既存suite同様の`undefinedFields`を用い、欠損・nullと区別する |
| 呼び出し結果 | `ok`とboolean値、または`invalid-input / timeout / unavailable / execution-error`等の機械可読エラー。使用したpackageHash、実行時間、相関IDを返す。エラーをfalseに変換しない |
| 受け入れ結果 `acceptance-report` | requestId、packageHash、要求hash、計画hash、runner版、シナリオごとの実際の呼び出しと観測値、`pass / fail / error / stopped`、理由。部品検証reportとは別に保存する |
| 修正依頼 `repair-request` | repairId、requestId、対象packageHash、要求ID、失敗段階、再現入力、期待値、実測値、ログ参照、固定suiteのhash、残予算・期限・残修正回数 |
| 配備 `activate` | requestId、packageHash、両検証記録、受け入れ計画hash、期待する現在の有効版。重複要求は同じ結果を返し、競合する更新は拒否する |
| 無効化・切り戻し | 対象ID、現在版、戻し先packageHash、理由。戻し先の保存成果物と合格根拠を再確認する。現在の要求・計画と適合しない旧版へ戻す場合は再受け入れする |

packageHashはS-LANGの`readCapability`が返す値を使い、独自のhash計算規則を作らないでください。現在はmanifestと各ファイルのhashを通じて成果物へ結び付きますが、署名や提出者認証ではありません。ローカルの信頼するジョブ・保存先から取得し、Coding Agentが書けないSAAA側領域へ候補と判定記録を保存します。

能力の説明やパッケージ中の自然言語はデータとして扱い、SAAAの権限や配備ルールを変更する指示として実行しません。受信時だけでなく、有効化時と呼び出し時にも検証済みの同じ成果物であることを担保してください。

## 検証と配備の規則

候補は「受信 → 部品再検証 → 受け入れ → 配備可能 → 有効」の順に進みます。failは修正待ち、errorは原因調査、予算・期限超過はstoppedとし、どの場合も有効化しません。旧版がある場合、候補の失敗で旧版を消さないでください。

今回のPoCでは、部品検証pass、未検証要求なし、受け入れ全件pass、対象hash一致を配備条件とします。変異reportは判定根拠とともに保存します。受付判定の基準候補では非同値のsurvived、unknown、error、未処理提案が0であることを確認します。変異検査の成功を要求全体の正しさの証明には使いません。

部品検証は合格するが受け入れで失敗する経路も必要です。そのための弱いsuiteと停止条件を欠く候補は、隔離した故障注入試験だけで作ります。通常の生成suiteや配備条件を緩めてこの経路を作らないでください。変異で既に拒否できた試験と、SAAAが利用上の誤りを検出した試験は別々に記録します。

SAAAの受け入れ失敗からの修正は、初回PoCでは最大1回です。要求、元の部品suite、受け入れ計画を固定し、公開した再現ケースを回帰テストへ追加します。追加前後のsuite hashと関係を保存し、元のケースを削除・緩和しません。現行developを再実行してsuiteを作り直すだけではこの要件を満たしません。専用の修正adapterはS-LANG側の追加作業とします。

SAAAの外側の1回と、develop内部の最大1回を別々に数え、ジョブ全体のモデル呼び出し・token・経過時間も集計してください。全体予算から各製造runへ割り当て、残量を超えるrunは起動しません。usage不明、同じ候補の再提出、再試行後の不合格では停止します。timeoutで結果不明の配備を無条件で繰り返さず、requestIdで状態照会します。

受け入れ非公開ケースを最初の製造依頼には含めません。修正時に開示したケースは既知の回帰試験となるため、未知ケースへの汎化を確認したと報告しないでください。受付判定は4通りしかなく、全列挙による正しさの確認と、SAAAの発見・入力作成・結果解釈の評価を分けます。

## 実装順序と担当成果物

| 段階 | SAAA側 | S-LANG側・共同作業 | 完了条件 |
| --- | --- | --- | --- |
| P1 契約固定 | 既存skill/tool登録口、製造ジョブ起動口、永続化先、実行環境を確認。依頼・計画schemaを実装 | 現行Source/metadataへの対応、schemaとエラー分類を合意 | 保存した依頼を読み直せ、不正入力・未知版を拒否できる |
| P2 受信・試験実行 | 候補を隔離保存し、再検証。通常と共通の呼び出し経路を試験名前空間へ接続 | Bunでの検証・単発呼び出しadapter、入力検査、timeoutを提供。現行内部APIを安定公開APIと誤認しない | fixture候補をSAAAホストから実Wasmで呼べる。配備前は一般の能力検索に出ない |
| P3 利用検証・修正 | シナリオrunner、独立report、失敗からの修正依頼、予算管理を実装 | 固定suiteを維持する修正入力と新候補提出を実装 | 部品合格でも利用失敗なら配備されず、修正後に同じ条件で合格する |
| P4 配備・復旧 | ローカルレジストリ、二段階gate、原子的有効化、無効化、切り戻し、再起動復元を実装 | hash照合と改変・競合試験を共同実施 | 通常会話から有効版だけを使え、更新失敗時に旧版を維持する |
| P5 実SAAA評価 | 実際のSAAAがタスクから能力を選択・利用する試験を実施 | 実Coding Agentでの製造を接続し、費用・失敗も記録 | fixture結果と実エージェント結果を区別した共同結果報告がある |

P1で接続先を確認し、P2〜P4の制御経路はfixtureで進められます。ただし実SAAAが能力を利用した証拠がない段階は「接続準備完了」であり、導入完了とはしません。実Coding Agentの製造品質も別の評価項目として残します。

## 必須の受け入れ試験

| 試験 | 合格条件 |
| --- | --- |
| 正常な能力取得 | 要求から候補、両検証、登録、通常呼び出しまで相関IDとhashで追跡できる |
| 能力発見と入力作成 | 名前を直接指定しない会話タスクから、適切な能力・boolean入力を選べる。LLMの説明だけで成功にならない |
| 範囲外タスク | 外部登録や数値計算をこの能力で完了したと誤報告しない |
| 不正入力と正常false | 必須値欠損・型不一致をエラーとして返し、受付不可とは区別する |
| 部品検証失敗 | SAAAの説明上の評価にかかわらず配備されない |
| 受け入れ失敗・修正 | 故障注入候補を拒否し、固定条件で修正版だけを配備する |
| 改変・古い判定 | 候補や計画のhashが変わった場合、以前の合格を流用できない |
| 重複・競合・途中停止 | 同じ依頼で重複配備せず、競合更新を検出し、再起動後も未完了候補を有効と誤認しない |
| 更新失敗・切り戻し | 旧版を保持し、戻した版の通常呼び出しを確認できる |
| 上限・改善なし | 期限、予算、修正上限、同一候補、usage不明で停止し、追加ジョブを起動しない |
| 権限分離 | Coding Agentが受け入れ記録や有効版を直接変更できず、改ざんした合格reportだけでは配備できない |

SAAA側の納品物は、接続adapter、受け入れrunner、ローカルレジストリと配備gate、修正依頼処理、上記の自動試験、起動・復旧手順、実行結果報告です。結果報告には両リポジトリのcommit、実行環境、fixtureか実モデルか、モデルと予算、各段階のhash・成否・費用・時間・停止理由を記載してください。

## 着手時にSAAA側から回答してほしい情報

1. SAAAのリポジトリ・対象branchと、能力を登録・検索・呼び出す既存インターフェース。
2. 実行環境とBunプロセスを動かせるか。別言語ホストの場合、まずローカルプロセス経由で接続できるか。
3. Coding Agentへの既存の依頼・結果取得方法。未整備なら初期接続先を1種類選ぶ。
4. 候補と受け入れ計画の保存先、Coding Agentとの権限分離方法、ジョブ全体の時間・token予算。
5. 実SAAA試験で使うモデル・認証設定と、機密入力を含めずにログを残せる範囲。

接続情報が未確定でもschemaとfixture試験の準備は進められます。外部公開、任意Wasm受信、外部操作を伴う能力、複数ホスト配布、一般的な自律改善loopは次段階とし、今回の完了条件には含めません。

## SAAA側の検討回答を受けた準備計画

接続先がTauri/Rustとpiであること、配布時Bunと自動製造の許可が未確定であることを踏まえ、[PoC準備計画](./SAAA_POC_PREPARATION_PLAN.md)を追加した。まずモデル不要の接続キットを用意し、その後に固定suiteを保つ修正と配備試験へ進む。配備条件の「未検証要求なし」は要求IDのcase対応を指し、現行reportの一般的な留保を含むunchecked全体が空であることは求めない。fixture試験での有効化先は試験レジストリに限定する。
