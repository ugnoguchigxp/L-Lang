# Binaryen の情報取得ガイド

目的: コーディングエージェントが必要な資料だけを段階的に読む。専用 MCP や検索基盤は不要。

## 読む順序

| 今の作業 | 次に読む資料 | そこで足りない場合 |
| --- | --- | --- |
| Wasm 生成コード、API、バージョン更新 | [API と実装](implementation.md) | 対象 emitter とローカル型定義の該当箇所 |
| 遅い・メモリが多い、最適化パスを選ぶ | [最適化と測定](optimization.md) | 実験記録、該当パスの公式説明・実装 |
| JSONC の生成だけ | 対象 profile の仕様・診断 | emitter を変更する必要が判明した場合だけ API 資料 |

両方にまたがるときは必要な順に二つ読む。リンク先を再帰的に全取得しない。API の名前・意味・検証方法が確定したら情報取得を止め、作業へ戻る。

## 情報の優先順位

1. 作業ツリーの仕様・対象実装・固定依存・インストール済み型定義。
2. そのバージョンの Binaryen 公式ソースとテスト。
3. 最新の公式ドキュメント。追加機能が固定版でも使えるとは仮定しない。
4. ローカルの性能記録。記録された入力・環境の範囲で解釈する。

2026-09-17 確認時の依存は Binaryen 132.0.0。値を永続的な事実とせず、変更時に `package.json` と lockfile、実際に解決されたパッケージを確認する。新 API／パスは固定版の小さな入力で動作確認してから使う。

## この導線の維持

Binaryen 更新や emitter / profile 追加時は、該当資料の参照と適用範囲も更新する。性能の一般則は少数に留め、個別の測定値は実験記録へ置く。

導入前はルート AGENTS.md と Binaryen 専用の案内がなく、コード・実験記録・外部資料の個別探索が必要だった。導入後は「短い入口 → 作業別資料 → 必要な箇所」の順で取得する。生成品質・速度が改善するかはまだ未測定。

文書変更の検証は `bun run src/verify-markdown-links.ts`。成功条件はリンク検査の合格と、表の各作業から参照先へ到達できること。失敗時は参照先を修正し、検査を弱めない。
