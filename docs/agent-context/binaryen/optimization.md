# Binaryen: 最適化と測定

読みどころ: 速度・メモリの改善候補を考えるとき。以下は生成と調査の指針であり、速度保証ではない。

## LLM に必要な最小知識

| 知識 | 判断への使い方 |
| --- | --- |
| 定数化・不要処理除去などは Binaryen に任せられる | 命令を手作業で細かく加工する前に既存パスを確認する |
| アルゴリズム・転送量・ホスト側 JSON 変換は別の層 | Wasm の命令最適化だけで解決しようとしない |
| 副作用・trap・評価順序は変換の成立条件 | 要求にない「エラーは起きない」等の前提を追加しない |
| インライン化等には速度とコード量の交換条件がある | 強い最適化設定を無条件に選ばない |
| 小さいバイナリは小さい実メモリと同義ではない | ファイルサイズ、linear memory、ホスト全体の RSS を分ける |
| 命令が少ない、分岐がないことは速さの保証ではない | 候補として生成し、同じ入力・ランタイムで測る |

LLM の出力が JSONC のみなら、profile が表現できる変更だけを行う。最適化ヒント用の未知フィールドを追加しない。表現できない改善はコンパイラ変更の提案として分ける。

## 詳しい情報が必要になった場合

[公式 Optimizer Cookbook](https://github.com/WebAssembly/binaryen/wiki/Optimizer-Cookbook)で該当項目だけ読む。

- 単純な出力が十分に整理されない: ReReloop / Converge の説明。既定パイプラインは最適化済み LLVM 出力を中心に調整されている。ただし反復によるサイズ縮小を速度改善とは扱わない。
- 関数呼び出し越しの最適化: Global effects の説明。作用解析がどの段階で有効か確認する。
- 意味上の前提を要求するオプション: Traps Never Happen や Low memory unused の説明。前提が仕様・実装で保証されない場合は使用しない。

Cookbook は最新版であり、記載パス・オプションが固定版に存在するかは[API 資料](implementation.md)の参照先で確認する。例示されたコマンド列をそのまま既定設定に採用しない。

## 候補の扱い

候補ごとに「対象処理」「変換」「成立条件」「期待する効果」「確認方法」を短く記録する。正しさを先に検証し、その後に性能を測る。入力検証やエラー処理を片方だけ省いた比較はしない。

計算単体と入出力込み時間を分け、メモリ目的ならホストを含む実メモリを測る。入力分布・サイズ、ランタイム、CPU、サンプル、実行順、バージョン、ソースと成果物のハッシュを保存する。未測定の候補を「高速」「省メモリ」と報告しない。

## ローカルの事例を読む条件

- O2 / O3、select / if、配列ソートに関係する場合: [段階評価](../../../examples/wasm-json-sort/STAGED_RESULTS.md)。selection の分岐書き換えは限定実験で、一般的な変換規則ではない。
- ホスト連携や入力変換が支配的な場合: [PoC 記録](../../WASM_POC_RESULTS.md)。終了付近の RSS をピークメモリの証拠にしない。
- 探索・採否・再現性を設計する場合: [最適化ビルド設計案](../../WASM_OPTIMIZED_BUILD_DESIGN.md)。未実装の提案として読む。

コンテキストの有効性自体は、知識なし／ありでモデル・予算・課題・コンパイラを揃えた複数回の比較で評価する。正答率、性能、取得量、生成・修正費用を記録し、資料を増やすだけで改善すると仮定しない。
