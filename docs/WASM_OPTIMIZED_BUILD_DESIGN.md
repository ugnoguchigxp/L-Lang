# Wasm 最適化ビルド設計案

状態: 議論用・未実装。2026-09-17。

安全性の保証境界、資源課金を含む意味保存、段階的な着手条件は、[メモリー安全性と Semantic IR 最適化のコンセプト](./MEMORY_SAFETY_AND_SEMANTIC_OPTIMIZATION_CONCEPT.md)（2026-09-20）を参照。本書の過去の前提と現行 profile の実装状況は区別する。

## 目的

Wasm ビルドを、継続利用する処理の実行時間と実メモリ使用量を減らすための経路として設計する。ビルド時間を長く許容し、実行時の負担を減らす。試作の TypeScript 経路と同じ要求・意味・受け入れテストを共有する。

ただし、共通の現行 JSONC IR から TypeScript と Wasm を出力する製品経路は、この提案の前提となる追加開発である。既存のソート example は専用テンプレートによる実験であり、現行言語の配列・数値・ループ対応を意味しない。

## 既存の証拠と限界

- [ソートの段階評価](../examples/wasm-json-sort/STAGED_RESULTS.md)では、7,100 件の heap の Wasm 計算部分は生成 TypeScript より約 2.1–2.2 倍速かった。一方、入出力を含む時間短縮は約 3–8% に留まった。
- 同じ実験の selection は O3 で遅くなり、特定の select を if に戻すと回復した。最適化レベルの増加だけでは速度を保証できない。
- [既存 PoC](WASM_POC_RESULTS.md)の RSS はプロセス終了付近の値であり、ピークや同条件の増分メモリを測ったものではない。Wasm の省メモリ性は未実証。
- 現行 Predicate は linear memory を使わない。配列用メモリ設計は新しい profile / ABI の仕事であり、既存の状態禁止契約を最適化の名目で変更しない。

## 対象と対象外

対象は、決定的なコンパイラ最適化、データ配置と ABI、対象ランタイム上の測定、候補選択、再現可能な成果物記録。初期対象は少数の実処理と一つの実行環境に限定する。

この文書ではコンパイラ実装、言語仕様変更、SAAA への組み込み、夜間ジョブや自動配備を実施しない。C / Rust / LLVM への全面移行も前提にしない。

## ビルドと探索を分ける

通常の最適化ビルドは、固定されたレシピで毎回同じ成果物を作る。夜間探索は、そのレシピを選ぶ別工程とする。

1. JSONC を検証し、共通の意味 IR を確定する。
2. 定数伝播・不要計算除去など、意味を保存する規則を適用する。
3. 型と処理単位に応じてデータ配置、ループ、バッファ寿命を決める。
4. Wasm を生成し、固定された Binaryen パスを適用する。
5. 正しさとリソース上限を確認する。
6. 探索の場合だけ、複数候補を対象環境で測り、採用するレシピを固定する。

LLM は候補の提案や測定結果の分析に利用できる。通常ビルドの必須依存にはせず、生成した変更も検証を通す。テスト合格は意味の完全な同値証明とは区別する。アルゴリズムの置換では、安定性・同値キーの順序・エラー挙動も契約に含める。

## 最適化の優先順位

| 層 | 方針 | 確認する効果 |
| --- | --- | --- |
| ホスト連携 | 呼び出しを適切な単位にまとめ、解析・検証・データ変換の重複をなくす | 入出力込み時間、コピー量 |
| メモリ配置 | 型付きの連続領域、必要な列だけの転送、上限付き作業領域 | ピーク実メモリ、作業領域の最大使用量 |
| 実行環境 | コンパイル済みモジュールを再利用し、インスタンス・キャッシュの保持量を制限する | 起動時間、常駐量、並行実行時のピーク |
| 計算 | IR と Binaryen のパス、分岐、ループ等を改善する | 計算時間と全体時間 |

外部入力の検証は維持する。検証済みデータを再利用する場合は、途中で変更できないこと、所有者と寿命が明確であることが条件となる。

JSON オブジェクトをホストに保持したまま全件コピーを複数作る構成を避ける。ソートなら、レコード全体を動かす方式とキー・インデックスだけを動かす方式を比較する。文字列の順位付け自体が高コストになる点も含めて測る。ホストの JSON と Wasm memory の間で無条件に zero-copy にできるとは扱わない。

バッファ再利用は割り当てを減らせるが、最大入力に合わせた容量を保持すると常駐量が増える。保持上限とインスタンス破棄条件を設ける。バッチ拡大にもメモリと待ち時間の予算を設ける。

## ランタイムの選択

最初に SAAA の実際の呼び出し方を固定する。既存の Bun 単発プロセス用キットと、ホストへの Wasm ランタイム組み込みは異なる構成である。

Rust ホストに Wasmtime 等を組み込めるなら、別の Bun プロセスを起動する方式との比較対象にする。プロセスやエンジン構成を変えることによる省メモリ効果は測定する仮説であり、現状の成果ではない。

Wasmtime の [事前コンパイル](https://docs.wasmtime.dev/examples-pre-compiling-wasm.html)は、コンパイルを要求処理の外へ移せる。ただし、これだけで定常実行速度や RSS が改善するとは判定しない。AOT 成果物はランタイム・CPU 等に依存する派生成果物として管理し、配布用 Wasm と区別する。

インスタンスプールは再生成の負担を下げる一方、保持メモリとの交換条件がある。[Wasmtime のプール設定](https://docs.wasmtime.dev/api/wasmtime/struct.PoolingAllocationConfig.html)も参照し、予約仮想アドレス量と実際に常駐するメモリを混同しない。

## 測定と採用条件

同一入力、同一検証、同一結果、同一並行数で次を比較する。

- 通常利用として妥当な TypeScript 実装。組み込みソート等も候補に含める。
- 同じアルゴリズムの生成 TypeScript。バックエンド差の診断用。
- 最適化前 Wasm と、現在採用中の成果物。

主指標は要求受付から結果生成までの時間と、ホストを含むプロセス群のピーク実メモリ。定常 RSS、起動時間、並行数固定の throughput、計算単体、変換時間、linear memory 容量、作業領域使用量、ファイルサイズも別々に記録する。小さい Wasm ファイルを省メモリの証拠にはしない。

入力は小・中・大、整列済み・逆順・重複・文字列長の偏り等を含め、探索に使わない保留データも用意する。ウォームアップ、複数プロセスでの反復、実行順交替を行う。p95 / p99 を採用する場合は十分な標本を集め、少数回の最大値を代用しない。

採用判定は以下の順とする。

1. 正しさ、セキュリティ境界、互換性が合格する。
2. 設定された遅延上限とメモリ上限を満たす。
3. 現行成果物からの退行を、事前に決めた許容幅内に抑える。
4. 比較対象 TS に対して速度と実メモリの両方に測定誤差を超えた改善がある場合、「高速・省メモリを確認済み」とする。

速度優先・メモリ優先の候補は、両方改善した候補と区別して提示する。改善率の閾値は実行環境の測定揺らぎと利用要件から決める。改善しない場合もビルドは有効だが、自動採用しない。結果不足は「不明」とする。

## 夜間探索と再現性

探索には候補数、実時間、CPU、メモリ、LLM 費用の上限を置く。標準パスの組み合わせから始め、独自変換は範囲を限定する。実験で有効だった select の書き換えを全プログラムに無条件適用しない。

記録するのはソース・意味 IR・成果物のハッシュ、コンパイラと Binaryen のバージョン、パス順と設定、ABI / profile、入力集合のハッシュ、測定方法、ランタイム・OS・CPU、全候補の結果と採否理由。時間等の可変な測定情報は決定的な成果物本体と分離する。

manifest の最適化設定はバージョン付きで拡張する。現行の固定設定を読む既存 verifier と replay の互換性も設計する。設定を無視して既定ビルドに戻す挙動は認めない。

夜間探索からの配備は将来の別機能とする。対象ソースが測定後に更新されていないことを確認し、既存成果物を保持して切り戻せる形で切り替える。レシピの選択と、実行中ホストへの採用は別の状態として記録する。

## 段階的な実装案

1. **測定基盤**: SAAA の実ランタイムを確認し、同条件の入出力込み時間とプロセス群のピークメモリを測る。試作 TS 経路をどの範囲で共通 IR 化するか決める。
2. **データ経路**: 配列用の別 profile で型付きバッファと上限付き作業領域を試し、変換・コピー・保持量の削減効果を確認する。
3. **最適化ビルド**: 固定レシピ、バージョン付き設定、正しさ検証、再現ビルドをコンパイラに組み込む。
4. **探索**: 上限付きの候補評価、保留データ評価、採否レポートを追加する。自動配備は実運用の契約が決まってから扱う。

代替案には現状の Binaryen のみ、Semantic IR から LLVM IR を直接生成する実験 backend、C / LLVM バックエンド、Rust / LLVM バックエンドがある。C/Rust ソース生成を必要としない直接 LLVM 案の範囲・意味保存・比較条件は、[LLVM を利用する独立した実験経路](./MEMORY_SAFETY_AND_SEMANTIC_OPTIMIZATION_CONCEPT.md#llvm-を利用する独立した実験経路)に整理した。いずれも未実装の提案であり、既存の直接 Wasm 経路を維持して代表処理一つから比較する。実行時間・実メモリ・ビルド時間・配布依存を合わせて判断し、LLVM を使っても JSON 変換やコピーの負担は別途評価する。
