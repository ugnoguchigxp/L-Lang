# SAAA PoC開始に向けた準備計画

2026-09-16。[SAAA側への依頼書](./SAAA_INTEGRATION_REQUEST.md)への検討回答を受けた準備案。今回は計画を具体化し、SAAAのコード変更、ジョブ起動、実モデル呼び出しは行わない。以下の新規CLI、schema、試験資材は未実装であり、提案値は双方で固定するまでは合意済み仕様としない。

## 方針

SAAAへ大きな依頼書だけを渡すのではなく、L-Lang側で「契約、呼び出せる実行adapter、正解と故障を含む候補、機械判定できる試験、再現手順」を揃える。SAAA側はそれをRustから接続し、受け入れと登録の制御に集中できる状態にする。

準備の完了を二つに分ける。

- **R1 接続試験開始可能**：Bun子プロセス経由で、候補の検査・部品検証・単発呼び出しができる。モデル認証、pi、自動製造、通常会話への公開は不要。
- **R2 P2〜P4のfixture縦断試験開始可能**：受け入れ失敗、固定テストを保つ修正、配備拒否、更新・復旧を再現できる資材がある。SAAA側のrunnerとレジストリをこの資材で検証する。

R1/R2は導入完了ではない。実会話での能力発見と、実Coding Agentでの製造はP5として別に評価する。配布済みアプリでの利用も、開発機での成功とは別の判定にする。

## R1までにL-Lang側で用意するもの

### 1. 両言語で共有する契約一式

JSON Schemaの正本、正常・異常のJSONサンプル、期待する検証結果を同じ版で配布する。TypeScriptとRustは同じサンプル集合に対して同じ合否を返す。追加プロパティ、未知の版、不正hash、過大入力、nullと欠損の違いも試験する。

最初に固定する対象は、検査・検証・呼び出しのrequest/response、候補提出、能力取得要求、受け入れ計画・結果、修正依頼、配備要求。schemaごとに書き手、読み手、改訂権限を定義する。

| データ | 正本を書ける主体 | 他方が行えること |
| --- | --- | --- |
| 要求・受け入れ計画・実行許可・予算台帳 | SAAAホスト | Coding Agentは参照可能な公開要求だけを読む |
| Source・suite・候補・製造記録 | Coding Agent / L-Lang製造処理 | SAAAは隔離コピーし、自分で検証する |
| 部品再検証・受け入れ結果・有効版 | SAAAホスト | Coding Agentは提出物や文章で合格を宣言しても更新できない |
| 修正の再現ケース | SAAAが公開、Coding Agentが回帰suiteへ追加 | 既存ケースの削除・緩和を禁止する |

requestId、invocationId、packageHash、要求hash、計画hashを用途別に定義する。相関IDは認証情報にしない。packageHashは既存`readCapability`の値を返し、Rustが独自計算しない。新しい計画・要求hashにはcanonical JSONの規則とテストベクトルを同梱し、順序や文字列符号化による不一致を避ける。

### 2. モデル不要の単発実行adapter

新規のプロセス契約案は「1起動・標準入力に1 JSON・標準出力に1 JSON」。操作はinspect、verify、invoke。adapterのCLI名とschema版はR1実装時に固定する。既存CLIの人間向け表示をRustが文字列解析する方式にはしない。

- Rustはshellを経由せず、設定済みの実行ファイルと固定argvで起動する。会話や候補metadataからコマンドを作らない。
- 候補参照はSAAA側のcandidateIdを管理下の絶対パスへ解決する。モデルに任意のファイルパスを渡させない。
- invokeは期待するpackageHashを必須にし、成果物の対応と入力契約を検査したsnapshotのWasm bytesを実行する。検証した後に別のbytesを読み直して実行しない。
- 入力はJSON objectとundefinedFields。存在する値との競合や重複指定を拒否する。正常なfalseとinvalid-inputを分離する。
- 出力はprotocolVersion、requestId、実行されたpackageHash、status、boolean値またはerror code、経過時間、apiCalls:0。未検証でhashが確定しないエラーではpackageHash:nullを許す。
- 構造化応答を返せた場合の終了コードは0とし、成否はstatusで判断する。不正JSON、出力欠落、非0終了、起動不能、期限超過はRust側のtransport errorとする。この規則は既存CLIの終了コードを変更せず、新adapterだけに適用する。
- 診断は上限付きstderr。stdoutへの進捗表示は禁止。Rustはstdout/stderrを同時に回収し、上限超過でも停止する。
- Rust側で期限を監視し、期限超過・cancel時は子プロセスを終了して回収する。Worker側のtimeoutだけに依存しない。子孫プロセスを作らない実行adapterとし、OSごとの終了試験を行う。
- 検証・実行経路ではコンパイラとモデルAPIを不要にする。APIキーは子プロセスへ渡さず、依存を固定したruntime一式を渡す。

単発invokeの成功は、その候補を通常利用へ公開してよいという判定ではない。試験用invokeと配備済みinvokeの許可はSAAAホストが分ける。

### 3. 再現できる接続キット

既存のaccess fixtureから、正しい候補、期待hash、部品検証report、4通りの受付入力と出力、不正入力を生成するコマンドを用意する。Wasmも含むキットを作るので、SAAA側がfixtureをコンパイルする必要はない。

配布物には契約版、L-Lang commit、Bunの検証済み版、ファイルhash一覧、生成方法、実行方法、期待結果を含める。絶対パスを埋め込まず、SAAAへコピーした別ディレクトリで動作確認する。hash一覧は真正性の証明ではなく、受け渡し元を別途信頼する前提とする。

Rust側はSAAAのtool登録前に、このキットだけで起動・入出力・timeout・キャンセル・パスの空白・再実行を試験できるようにする。

## R2までに追加するもの

### 固定テストを保つ修正adapter

入力は旧候補hash、固定Sourceと元suite、SAAAが開示した再現ケース、要求hash、残予算。元ケースを保持したsuiteへ回帰ケースを追加し、矛盾・重複・契約違反を検査してから実装だけを修正する。期待値が矛盾する場合は仕様確認待ちとし、自動で片方を消さない。

旧suite hash、追加後suite hash、親packageHash、新packageHashを記録する。Source・要求・受け入れ計画を変える必要があれば、修正ではなく新revisionとして受け入れをやり直す。修正は1回、同じ候補の再提出は停止。最初は保存済み応答を使い、モデル・piを起動しない。

### 失敗を含む試験セット

| 資材・試験 | SAAA側が確認すること |
| --- | --- |
| 正しい候補 | 再検証・利用受け入れを経て試験レジストリへ登録できる |
| 部品テストで落ちる候補 | 受け入れ前に止まり、有効版を変えない |
| 部品合格だが停止条件を欠く候補 | 独立した受け入れで失敗し、再現情報を修正へ返す |
| 修正版 | 元ケースと追加ケースが残り、別hashとして再受け入れされる |
| 改変済みWasm・古いreport・別計画hash | 配備時と実行時に対象不一致を拒否する |
| ハング・出力破損・途中終了する模擬adapter | ホスト側timeoutとエラー分類を確認する。悪意あるWasmの安全性を証明したとは扱わない |
| 重複配備・並行更新・保存途中で停止 | 二重登録しない。有効版の比較更新が競合を検出し、再起動で未完了版を公開しない |
| 更新失敗・切り戻し・無効化 | 旧版維持と通常呼び出し先の切り替えを確認する |

弱いsuiteは受け入れ失敗を注入するための専用fixtureとする。通常の配備gateを弱めず、mutationで拒否される経路とは分けて試験する。実行・検証までは本物のWasmを使い、会話と製造応答だけをfixtureで置き換える。

## SAAA側で用意してもらうもの

1. **PoC専用の入口**：既定無効。ユーザーが明示的に開始したPoC sessionだけを実行する。fixtureモードではcoding_startを呼ばない。将来の能力発見による自動起動許可は別の方針として扱う。
2. **Rust子プロセス接続**：上記プロトコルと総時間制限。開発用Bunパスは起動時に検査し、未導入ならunavailableで止める。自動インストールはしない。
3. **隔離コピーと記録**：候補は一時領域へコピーして全体を検査後、内容hashで保存する。SQLiteで要求・候補・判定・有効版を管理し、未完了を有効と誤認しない復旧処理を持つ。
4. **独立した受け入れrunner**：部品suiteの再実行だけで終わらせず、試験名前空間からの能力選択・入力作成・出力処理を観測する。fixtureでは同じ呼び出し経路へ固定tool callを与える。モデルの能力選択品質は測定したと扱わない。
5. **二段階の配備gate**：部品再検証pass、要求対応に欠落なし、独立受け入れpass、要求・計画・候補hash一致、現在版一致を検査する。fixtureの有効化先は試験レジストリに限定する。
6. **予算台帳と結果報告**：session全体で消費量を持ち、子ジョブへ残量を配分する。両commit、契約版、環境、実行モードと各試験の根拠を保存する。

現行部品reportのuncheckedには、常にSAAA acceptanceや自然言語完全性の留保が含まれる。「uncheckedが空」を配備条件にしてはいけない。要求欠落はrequirementsのcaseIdsと`requirement:`項目で判定し、SAAA acceptanceは別reportで満たす。自然言語全体の保証がないという留保は残す。

## 権限分離とBun配布の扱い

同じOSユーザーで無制限に動くCoding Agentは、別フォルダやSQLiteでも書き換えられる可能性がある。「SAAAだけが書く」という実装規約と、OSが強制する書き込み制限は別である。

R1/R2は実Coding Agentを起動しないため、信頼するfixtureのみで制御経路を試せる。P5の実Coding Agent接続前には、workspace限定sandbox、別ユーザー、コンテナ等から実際に採用できる方式を選び、SAAAのDB・候補保管領域・判定記録への書き込みが失敗する試験を行う。成立しない場合は、実Agentによる自動配備を保留し、権限分離まで検証済みと報告しない。hashだけではこの問題を解決できない。

BunについてはR1を「開発機にインストール済みの固定版を明示指定」で開始する。配布アプリでは、Bun同梱、実行可能ファイル化、別runtime等の選択が必要で、現時点では採用方式を確定しない。Worker同梱、署名・配布、クリーン環境での起動を検証するまでは、開発PoC成功を配布対応成功と扱わない。これをR1の前提条件ではなく、配布対応の開始条件にする。

## 予算とログの初期提案

数値はPoCの初期値であり、性能の保証ではない。実装時に設定として固定し、結果を見て同じsessionの上限を緩めない。

| 項目 | R1/R2 fixture案 | P5への移行条件 |
| --- | --- | --- |
| 外部モデル呼び出し | 0、認証情報不要 | モデル・実リクエスト認証・全体token上限を事前固定 |
| session時間 | 10分 | 実Agent用の期限とcancel完了を検証 |
| 単発invoke | ホスト15秒、Wasm側最大10秒 | 実測で調整する場合は設定revisionを更新 |
| verifyプロセス | ホスト30秒 | サイズ上限内で期限超過ならerror。自動延長しない |
| プロトコルサイズ | stdin 64 KiB、stdout 1 MiB、stderr 64 KiB | 超過時停止。既存成果物サイズ制限も維持 |
| SAAAからの修正 | 最大1回 | 内部修正と区別し、全体の再試行上限を維持 |
| ログ | 合成データのみ。ID/hash/状態/時間/エラー分類を保存 | secretsを記録せず、実入力・応答の保存と保持期限を別途固定 |

P5で使うtoken値を認証・モデル未定のまま仮に有効化しない。fixtureではtoken予算0を明示し、予算切れは模擬usageで制御経路だけを試験する。usage不明なら追加ジョブを停止する。モデル登録probeの成功は、認証・応答・品質確認の代わりにならない。

## 実装順序と開始判定

| 順序 | 担当 | 成果物と完了証拠 |
| --- | --- | --- |
| A 契約案を機械可読化 | L-Lang、SAAAがレビュー | schemaと共通テストベクトル。所有者、エラー、hash、予算規則を固定 |
| B 単発adapterと接続キット | L-Lang | 別ディレクトリでinspect/verify/invoke、改変拒否、timeout試験が成功。これでR1 |
| C Rust接続と試験名前空間 | SAAA | モデルなしで実Wasmを呼び、候補が通常会話に出ない。Bun不在・cancel試験も成功 |
| D 修正adapterと故障資材 | L-Lang | 旧suite維持・回帰追加・新hash・矛盾拒否を再現。これでR2 |
| E fixtureの受け入れ・配備・復旧 | SAAA | 独立判定、配備gate、重複・競合・再起動・切り戻しの証拠 |
| F 実SAAA・実Coding Agent評価 | 双方 | 権限・認証・予算を満たしてから実行。能力発見と製造品質を別々に報告 |

直近のL-Lang実装テーマはAとB、つまり**「SAAA接続契約とモデル不要の単発Wasm実行キット」**とする。SAAAはAのレビューとRust側ハーネスを進め、修正adapterの完成を待たずにR1へ着手できる。Dは次の独立した実装単位とする。

SAAA側への引き渡し時には、キットのcommitと取得方法、検証済みBun版、起動コマンド、schema版、期待値、既知の未対応事項を一覧にする。A〜Bが未完の現時点は「準備計画あり」であり、「PoC開始資材が揃った」とは報告しない。
