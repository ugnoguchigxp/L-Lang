# Wasm最適化の段階的調査（2026-09-17）

**最適化レベルを強めるだけでは改善しませんでした。選択ソートでは、最適化で導入された`select`を`if`へ戻すと約3.3倍速くなりました。一方、7,100件のヒープソートではO3のWasmが生成TSの約2.1〜2.2倍の速度でした。**

対象はExample専用の実験用コンパイラです。標準L-LangのPredicate profileは変更していません。旧記録は[RESULTS.md](./RESULTS.md)に残しています。

## 第1段階：最適化条件を明示して比較

前回は`setOptimizeLevel(2)`だけを設定し、Binaryen 132.0.0の既定`shrinkLevel=1`が残っていました。速度向けO2と同じ条件ではなかったため、今回4条件を明示しました。`legacy`で前回のTS/Wasmハッシュを再現できることをテストしています。

| 指定 | optimize | shrink | 意味 | Wasm bytes |
| --- | ---: | ---: | --- | ---: |
| none | 0 | 0 | 生成時の最適化パスなし | 1092 |
| legacy | 2 | 1 | 前回のサイズ縮小も含む設定 | 935 |
| O2 | 2 | 0 | 速度向けO2 | 944 |
| O3 | 3 | 0 | 速度向けO3 | 1051 |

100KiB／710件、3キー×5方式を全条件で実行。各条件は独立プロセス、15 samples × 10回、warmup 30回。2周目は設定とjobの順序を反転しました。以下は年齢の選択ソートで、2回のrunそれぞれの中央値の範囲です。単位はms／回。

| 設定 | TS本体 | Wasm本体 | Wasm全処理 |
| --- | ---: | ---: | ---: |
| none | 0.1163〜0.1223 | 0.1473〜0.1512 | 0.4123〜0.4501 |
| legacy | 0.1224〜0.1255 | 0.5200〜0.5210 | 0.8179〜0.8307 |
| O2 | 0.1187〜0.1200 | 0.4969〜0.5002 | 0.7831〜0.7851 |
| O3 | 0.1149〜0.1173 | 0.4870〜0.4969 | 0.7561〜0.7697 |

O2/O3でも最適化なしより遅く、shrink設定だけでは説明できません。したがって、O3へ上げるだけの変更や、すべての最適化を無効にする判断には進みません。

最適化なしでもBunの実行エンジンはWasmから機械語を生成します。ここで切り替えたのはBinaryen側の生成時最適化です。生成・最適化時間も生データに保存しましたが、各プロセス1回の起動時観測なので、性能分布を測ったものではありません。

## 第2段階：命令の変換を1か所だけ戻す

最適化後の選択ソートでは、最小位置の更新が`if`から`select`へ変わっていました。O3ではロード関数などの呼び出しも展開されていましたが、遅さは残りました。

```text
最適化後：min = select(j, min, value[j] < value[min])
比較版  ：if (value[j] < value[min]) min = j
```

他の最適化を維持し、対象関数のこの1か所だけを戻しました。両値が副作用のないlocal読み出しで、else側が元の代入先と同じ形だけを許可する実験用の変換です。一般的なselect除去ではありません。変更後に再度Binaryen最適化はかけず、両validatorを通して出力しています。

| 設定 | Wasm本体 | Wasm全処理 | Wasm bytes |
| --- | ---: | ---: | ---: |
| none | 0.1459〜0.1461 | 0.4130〜0.4140 | 1092 |
| O2 | 0.4857〜0.4886 | 0.7561〜0.7614 | 944 |
| O2-branch | 0.1476〜0.1497 | 0.4197〜0.4258 | 944 |
| O3 | 0.4906〜0.4929 | 0.7625〜0.7726 | 1051 |
| O3-branch | 0.1480〜0.1496 | 0.4294〜0.4348 | 1051 |

`if`に戻すと、O2/O3のどちらも最適化なしに近い速度へ戻りました。**生成WATは選択ソート関数以外に差がないことも4組で確認しています。** O3の対象関数は`select`の静的出現数が1→0、`if`が2→3となり、ロード4か所・call 0か所は変わっていません。Wasmサイズはどちらも1,051 bytesです。

これは今回のBun／CPU／入力で、当該命令形が性能に影響したという証拠です。最小位置を次のメモリアドレスに使う依存関係や分岐予測が関与する可能性はありますが、ネイティブ機械語・CPUカウンタは採取しておらず、CPU内部の原因までは断定しません。

比較版は`--selection-branch true`で選ぶ診断用の実装に留めました。全アルゴリズムへの一括適用や標準L-Langへの導入はしていません。

## 第3段階：710→3,550→7,100件

固定seedの生成データを先頭から増やしました。最初の710件は同梱fixtureと完全一致します。年齢の選択ソートとヒープソートを対象に、9 samples × 3回、warmup 10回で全条件を統一。独立プロセスで2周目は件数と設定の順序を反転しました。第1・2段階とは測定回数が異なるため、段階間の小差を改善量として扱いません。

| 件数 | JSON bytes | 選択 none | 選択 O3 | 選択 O3＋if | ヒープ TS（O3比較時） | ヒープ Wasm O3 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 710 | 102,503 | 0.1515〜0.1536 | 0.4949〜0.5150 | 0.1534〜0.1686 | 0.0156〜0.0157 | 0.0111〜0.0112 |
| 3,550 | 516,194 | 3.4233〜3.5445 | 9.7904〜10.4217 | 3.5744〜3.6677 | 0.1367〜0.1621 | 0.0678〜0.0728 |
| 7,100 | 1,033,169 | 13.4630〜14.3094 | 28.5714〜30.7445 | 13.1773〜14.0890 | 0.3397〜0.3452 | 0.1576〜0.1604 |

表はソート本体、単位はms／回です。選択ソートの不利な変換は件数を増やしても改善せず、if版の改善が維持されました。一方、7,100件のヒープソートではO3 Wasm本体がTSの約2.1〜2.2倍の速度となりました。

7,100件のヒープソートの全処理は、正順runがTS 3.1307ms／Wasm 3.0375ms、逆順runがTS 3.3140ms／Wasm 3.0464msです。本体の差に比べ、全処理での短縮は約3〜8%と小さくなります。3,550件ではrunによって全処理の優劣も入れ替わりました。

## 判断と次の対象

- 最適化設定はoptimizeとshrinkを組で固定し、manifestへ記録する。既定は過去の出力を維持する`legacy`のまま。
- O3を一律に推奨しない。特定の変換が逆効果になることがあり、代表入力で結果一致と性能を確認する。
- 今回のif版は原因を絞るための実験。標準パスにするには、ほかの入力分布・実行エンジンでも調べる必要がある。
- 高速なアルゴリズムではホスト前後処理の割合が大きい。次の実用性能調査は順位付けの除去や通常のArray.sortとの比較が候補。

今回のデータは固定seedで、キーの重複率にも偏りがあります。文字列・数値の順位付けをホストで行う従来の前処理は維持しました。したがって、Wasm単体のJSON解析・文字列比較性能や、任意の業務処理の速度は示していません。Bun 1.3.14、Apple M4、macOS arm64での探索結果です。CI指定のBun 1.4.2では未計測です。

## 再実行と保存物

```bash
bun run examples/wasm-json-sort/study.ts optimization artifacts/wasm-json-sort/my-stage1
bun run examples/wasm-json-sort/study.ts selection artifacts/wasm-json-sort/my-stage2
bun run examples/wasm-json-sort/study.ts scaling artifacts/wasm-json-sort/my-stage3

# 単独の比較版
bun run examples/wasm-json-sort/run.ts --optimization O3 --selection-branch true --key age --algorithm selection --records 7100
```

出力先は新しいディレクトリを指定します。各studyはプロセスを並列化せず、終了後に生成物と出力を確認してから次へ進みます。性能測定中に別のstudyを同時実行しないでください。

ローカルの完全な証拠は`artifacts/wasm-json-sort/stage1-optimization/`、`stage2-selection/`、`stage3-scaling/`にあります。各runのJSON結果、生成TS/Wasm、最適化前後WAT、source snapshot、ログ、report、SHA-256を保存しています。Git管理外のため、要約ではなく各sampleを含む計測JSONをこのExampleのevidenceにもコピーしました。

3段階で48プロセス、計160のjobを実行しました。各jobのTS・Wasm・独立オブジェクトソート結果が一致し、320個の保存結果JSONをハッシュで検証しています。時間計測中の毎反復でも、検証をタイマーの外で実施しています。

検証：専用テスト11件／1,224 assertions成功、全体型検査成功。対象Exampleのlint・整形、文書リンク検査も成功しました。全体テスト・カバレッジ・別OSのCIは今回の検証範囲に含めていません。
