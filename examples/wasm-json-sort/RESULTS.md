# JSONソートの実測結果（2026-09-17）

Example専用の実験用コンパイラから生成したTypeScriptとWasmの比較です。標準L-LangのPredicateコンパイラがソートに対応したことを示す結果ではありません。生成の仕組み・再実行方法・制限は[README](./README.md)を参照してください。

入力は**102,503 bytes、710件**。name・age・raceの3キーと5方式の全15通りで、両形式の出力と独立したオブジェクトソートの結果が一致しました。正順・逆順の2プロセスで確認しました。

追記：後続調査で、初回は最適化レベル2に加え、Binaryenの既定サイズ縮小レベル1が適用されていたことを確認しました。速度向けO2/O3、最適化なし、命令形変更の比較は[段階的調査](./STAGED_RESULTS.md)に記録しています。

## 条件

- 環境：Bun 1.3.14、Apple M4、darwin 25.6.0 arm64。CI指定のBun 1.4.2とは異なります。
- Binaryen 132.0.0、最適化レベル2。各方式でwarmup 30回、15 samples、各sample内10回。
- 各sample内のTS/Wasmの実行順は交互。別プロセスでjob順を反転。
- 単位は1回あたりms。sample平均の中央値。生のsample・最小・最大はJSONに保存。
- kernelは順位付け済み整数列のソート。end-to-endはJSON解析・検査・順位付け・コピー・ソート・復元・JSON文字列化。ファイルI/O・生成・起動は除外。

## この結果から分かること

挿入ソートではWasm kernelがTSの約1.6〜1.7倍の速度でした。一方、選択ソートではWasm kernelに約4倍の時間がかかりました。シェルソートはkernelではWasmが速いものの、全処理では小差です。ヒープソートも全処理の差は小さく、Wasmの一律な優位は見られません。

したがって、処理量を増やすと違いは観測できますが、「複雑になれば必ずWasmが速い」とは言えません。この実装では生成される命令・実行エンジン・アルゴリズムにより傾向が変わります。原因を特定するには生成命令とエンジン側の実行を別途調査する必要があります。

また、nameの全処理はageより時間がかかっています。文字列の順位付けなどホスト処理を含むためで、Wasmの文字列比較性能を測った結果ではありません。順位付けはホストのソートを含み、ユニークなキーが多いほどホスト側で順序決定の相当部分を済ませます。

100KiBでもレコード数は710件です。高速な方式ではkernelは十数µs程度なので、小差を一般化できません。通常のArray.sortより実用的に有利であること、LLVMに変更すれば改善すること、標準L-Langの性能をこの結果で証明することはできません。
